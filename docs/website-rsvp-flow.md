# Website RSVP Flow

## Purpose

Allow a guest who is not a registered Crew user to respond to an event through a publicly shareable RSVP link. The website is a static GitHub Pages frontend; Supabase validates the invitation and records the response.

## Product Flow

1. The Crew app creates a secure RSVP token for an invitee and associates it with the activity/invitation in Supabase.
2. The app creates an HTTPS link containing the token and opens the phone's normal share sheet.
3. The inviter sends the link through SMS, WhatsApp, email, or another messaging app. Crew does not send messages for the MVP.
4. The guest opens the static RSVP page, which reads the token from the URL.
5. The guest enters their name and chooses `Going`, `Maybe`, or `Can't Go`.
6. The website sends the token and response to a Supabase Edge Function or secured database RPC.
7. Supabase validates the token, returns only the permitted event payload, and records the RSVP.
8. The event coordinator sees the guest's response through the existing Crew app owner flow.

The guest may update their response later with the same valid token. The coordinator can revoke the token, after which the website must reject reads and submissions.

## Link Design

Use an opaque, cryptographically random token generated by the app. Because the site is hosted on GitHub Pages, prefer a query-string URL that works with static hosting:

```text
https://yourdomain.com/rsvp?token=<opaque-token>
```

The token must not contain an activity ID, email address, name, or other readable personal data. Store only a hash of the token in Supabase. The token must be scoped to one activity and one invitation, and must support expiration and revocation.

The app owns token generation and link creation. The website must never generate invitation tokens or expose token-management operations.

## Website Experience

The static RSVP page should provide:

- A loading state while the token is validated
- Event title, date, time, location, and relevant description after validation
- A required guest-name field
- `Going`, `Maybe`, and `Can't Go` actions
- The guest's current response, if one exists
- A confirmation state after a successful submission
- Clear states for missing, invalid, expired, or revoked tokens
- Optional calendar download only after the event payload has been authorized

The browser should receive only the event details and the invitation's own RSVP state. It must not receive the complete guest list, private account information, raw database records, or other event data outside the validated invitation's limited payload.

## Suggested Data Model

The app/backend should maintain a separate external invitation or guest RSVP record associated with an activity:

- `activity_id`
- `token_hash`
- `guest_name` (required once the guest responds)
- `status` (`pending`, `going`, `maybe`, `cant_go`, `revoked`)
- `expires_at` (optional)
- `responded_at` (optional)
- `created_at`
- `updated_at`

An invitee email or phone number may be retained if the app already has it, but it is not required for the MVP and must not be required for website access. Keep external responses separate from authenticated-user RSVPs while allowing coordinator attendance queries to aggregate both sources.

## Security Requirements

- Generate tokens with a cryptographically secure random generator in the app/backend.
- Store token hashes, never raw tokens.
- Validate the token before returning event details or accepting an RSVP.
- Restrict each token to one activity and one invitation.
- Enforce expiration and owner-controlled revocation.
- Validate the response against the supported statuses on the server side.
- Rate-limit token validation and RSVP submission.
- Do not expose the full invitee list or private account data.
- Avoid logging raw tokens, guest names, or contact details unnecessarily.
- Use Supabase Row Level Security and/or a narrowly scoped security-definer RPC or Edge Function.
- Keep Supabase credentials out of the repository. A browser may use only the public anonymous key, with RLS and server-side validation enforcing access.
- Treat the token as a bearer credential: anyone with the link can act as that invitee until it expires or is revoked.

## Static Hosting Architecture

```text
Guest opens GitHub Pages RSVP page
        ↓
Browser reads ?token=...
        ↓
Supabase Edge Function or secured RPC validates token
        ↓
Supabase returns limited event payload
        ↓
Guest submits name and RSVP status
        ↓
Supabase records response
        ↓
Coordinator sees response in Crew
```

GitHub Pages provides the static HTML, CSS, and JavaScript only. It does not provide server-side route handling, private environment variables, or database access. Supabase owns validation, authorization, and persistence.

## Attendance Counts

The coordinator-facing `# Attending` count should aggregate:

- Authenticated app users with an RSVP status of `going`
- External invitations/guest RSVPs with a status of `going`

Detailed lists should distinguish authenticated attendees from external guests, while both contribute to the total attendance count.

## Functional Slices

### Slice 1: App-Generated Invitation Tokens

- Generate a unique token for each invitee in the existing app/backend flow.
- Store only the token hash with the activity invitation.
- Create the shareable RSVP URL.
- Open the phone's native share sheet.

### Slice 2: Supabase Validation and RSVP Operations

- Add a narrowly scoped Edge Function or secured RPC for token validation.
- Return a limited event payload only for a valid, active token.
- Accept guest name and supported RSVP status.
- Record or update the guest response.
- Cover valid, invalid, expired, revoked, duplicate-submission, and update cases.

### Slice 3: Static Website RSVP Page

- Read the token from the query string.
- Handle loading, success, missing-token, invalid, expired, revoked, and error states.
- Collect the guest name and response.
- Never load the event payload before token validation.
- Add browser tests for each response and state transition.

### Slice 4: Coordinator Integration

- Show external guest responses in the existing event-owner flow.
- Include external `going` responses in attendance counts.
- Support token revocation from the coordinator workflow.
- Add end-to-end coverage from app link creation through website response.

### Later Enhancements

- Optional email or phone verification
- Invitation reminders
- Calendar download after responding
- Guest account creation or RSVP claiming
- Guest photo or other post-event participation

## Explicit Non-Goals for the MVP

- Crew-sent email, SMS, or WhatsApp messages
- An email delivery provider or resend system
- Guest account creation
- Public event or invitee-list browsing
- A shared event ID link as the primary design

## Open Decisions

- Whether `guest_name` is required before viewing event details or only before submitting
- Token expiration duration
- Whether the app generates one token per invitee or one token per share action
- Whether calendar download is included in the first website release
- Whether the Supabase integration should use an Edge Function, a database RPC, or both
